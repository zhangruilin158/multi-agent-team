# 统一角色池（Unified Role Pool）

> 把两个来源角色库合并、去重、按领域归类后的**单一角色池**。
> 团队创建流程**只认这一个池**——禁止再分别查两个源库，避免重复角色与命名冲突。

## 1. 池的构成

| 来源 | 角色数 | 领域数 | 说明 |
|------|--------|--------|------|
| 通用角色库（英文总库） | 267 | 19 | 通用角色主库，按部门组织 |
| 中文角色库 | 265 | 20 | 中国本地化角色 + 公司/HR/法务/供应链等特有领域 |
| 工程专家人设库 | 21 | — | 工程向专家人设（架构/后端/安全/SRE/DevOps…） |
| 评审专家人设库 | 4 | — | 评审向专家人设（代码/安全/测试/Web 性能） |
| 前两库同名（slug 相同） | 214 | — | **去重合并为 1 条** |
| 后两库判定重复 | 21 | — | 与池内已有角色语义重复，**不新增**，仅登记别名（见第 7 节） |
| **合并后（唯一角色）** | **322** | **23** | 团队可引用的实际角色总数 |

> 计算：267 + 265 − 214（前两库去重）= 318；再 + 21 + 4 − 21（后两库重复）= **322**。

源库实际路径（体积大，不进技能包，已下载到工作区 `ai-agent-frameworks/`）：
- 通用角色库：`ai-agent-frameworks/通用角色库（英文总库目录）/<领域>/<slug>.md`
- 中文角色库：`ai-agent-frameworks/中文角色库目录/<领域>/<slug>.md`
- 工程专家人设库：`ai-agent-frameworks/工程专家人设库目录/personas/<slug>.md`
- 评审专家人设库：`ai-agent-frameworks/评审专家人设库目录/agents/<slug>.md`

## 3. 合并与去重规则

1. **主键 = slug**（角色文件名去掉 `.md`，如 `engineering-code-reviewer`）。两库 slug 完全一致即视为同一角色。
2. **双库共有** → 合并为**一条**记录：
   - 名称：通用库英文名作 canonical，中文库名作「中文别名」；
   - 职责 / 能力：取通用库原文为主，中文库作中文镜像；
   - 来源标注为「双库共有」。
3. **仅单库存在** → 直接入池，来源标注「仅通用库」或「仅中文库」。
4. **禁止**出现两条 slug 相同、或同一领域内名称相同的记录。

## 4. 角色条目规范（唯一性约束）

每条角色**有且仅有**以下字段，且**名称、职责、能力描述在同一领域内必须唯一**：

| 字段 | 含义 | 取自源文件的哪一行（真实结构） |
|------|------|-------------------------------|
| `slug` | 角色唯一标识 | 文件名（去 `.md`） |
| `name` 名称 | 角色名 | frontmatter `name:` |
| `role` 职责 | 这个角色负责什么 | **通用 / 中文角色库**：正文 `- **Role**:` / `- **角色**：` 行；**工程 / 评审专家人设库**：这两库**没有**该行，改取 `# <名称> - <职责>` 标题或 `## Core Identity & Mission` 首段 |
| `capability` 能力 | 这个角色能做什么 | frontmatter `description:` |
| `domain` 领域 | 所属领域 slug | 所在目录名 |
| `source` 来源 | 双库共有 / 仅通用库 / 仅中文库 | 按第 3 节判定 |

**唯一性检查**：新增或引用角色前，确认该领域内不存在相同的 `name`、`role`、`capability`；重复则合并或重命名（加领域后缀区分）。

**条目示例**（真实结构映射）：
```yaml
slug: engineering-code-reviewer
name: Code Reviewer（中文名：代码审查员）
role: 代码审查与质量保障专家
capability: 提供建设性、可操作的反馈，聚焦正确性、可维护性、安全性和性能，而非代码风格偏好
domain: engineering
source: 双库共有
```

## 5. 团队创建流程如何引用

**引用格式**：`统一角色池/<领域>/<slug>`

落到 `team_config.py` 的 `TEAM` 时，每个角色条目**必须**带 `domain` 与 `source` 两个字段：

```python
TEAM = [
    {
        "domain": "engineering",           # 领域 → 决定归属哪个领域小组
        "source": "engineering-code-reviewer",   # 统一角色池 slug
        "role": "代码审查员",
        "goal": "找出正确性与安全隐患",
        "backstory": "审查过上千 PR，重教学而非批判",
    },
    # 库外新建的角色：source 以 new: 开头
    {"domain": "product", "source": "new:pricing-analyst", "role": "定价分析师", ...},
]
```

- 命中池中角色 → `source` 填池内 slug，**直接复用其人设，不重写**；
- 池中确实没有 → `source` 填 `new:<自定 slug>`，并保持相同的 `role/goal/backstory` 结构。

## 6. 领域小组最低人数

- **每个领域必须分配 2 名及以上专家**，组成一个领域小组。
- 领域可选角色 < 2 时（当前仅 `research` 合并后为 1），从语义最近的领域（`academic` / `specialized`）**跨领域补齐**到 2 人。
- 小组人数 = 该领域在 `TEAM` 中 `domain` 相同的条目数，由 `build_team.py` 校验（不足会告警）。

### 7.3 去重判定口径

1. 先按 slug **精确**匹配；再按**语义**匹配（职责与能力描述高度重合即判重复）。
2. **通用 vs 专项不互相覆盖**：专项角色（如仅 Rust 的重构）不覆盖通用角色，两者可共存。
3. 判重复的只登记别名，**不占用新 slug**，避免同领域重名或职责重复。
4. 后两库的人设本身仍可阅读参考，但**组队时必须改用上表右侧的池内角色**，保证全池唯一。
